## 详细记录

### 2026-11-01 · v2.11.10 · 邮件服务可用性判断与通知模板

- **修复**：管理后台已经配好并按「测试邮件」成功，但用户「通知设置」里仍显示「管理员还没有配置邮件服务」，开关不可点。
- **根因**：可用性原来只来自 `GET /api/settings`，而该接口以「选中的账号」为前提；通知设置页在没选账号时不会请求它，前端就停留在默认的 `available: false`。
- **改法**：新增 `GET /api/settings/mailer`（与账号无关，仅返回 `{available, senderName}`），前端 `useSettingStore.fetchGlobalMailer()` 在进入设置页时无条件调用一次。
- **新增模板**：管理后台「邮件通知」加入四个常用模板（维护更新 / 续费提醒 / 功能更新 / 服务恢复），点击后一键填入主题与正文，正文里已写明「维护后需要重新登录账号」等操作步骤。
- **验证**：`pnpm -C web build`、`pnpm -C web lint` 通过，全量单测 563 项通过。

### 2026-11-01 · v2.11.9 · 修复全局邮件设置保存报错

- **修复**：管理后台「全局设置 → 全局邮件服务」在保存、读取、测试时都会报 `next is not a function`，界面看起来「点了没反应」。
- **根因**：`registerAdminMailerRoutes` 把 express 中间件 `requireAdminRole(req, res, next)` 当普通函数调用（只传了 `req`、`res`），中间件内部 `next()` 抛错，被统一 catch 成 500。
- **改法**：邮件相关五个路由改成标准中间件挂载 `app.get(path, requireAdminRole, handler)`，不再手动调用；未注入中间件时退化为放行。
- **验证**：新增回归测试校验「每条邮件路由都挂载了中间件」以及「超级管理员放行 / 普通用户 403」；用真实 express + 真实 `requireAdminRole` 跑通 `GET /api/admin/mailer`(200)、`GET /api/admin/mail-recipients`(200)、普通用户 403；全量单测 563 项通过。

### 2026-10-29 · v2.9.4 · 修复构建时依赖源不可用

- 现象：`./start.sh` 选 1 或 2，镜像构建走到 `RUN pnpm -C core install --prod --frozen-lockfile` 直接失败，报 `Error when performing the request to https://registry.npmmirror.com/pnpm/10.30.2` 与 `ETIMEDOUT 116.117.158.52:443`。
- 原因：`core/Dockerfile` 用 `corepack enable` 安装 pnpm，而 corepack 每次都要联网去镜像源拉 pnpm 本体。镜像源一旦不可达，整次构建就失败；之前能构建成功只是因为那一层还在本地缓存里。
- 修复：不再使用 corepack，改用 npm 安装 pnpm（版本取自 `package.json` 的 `packageManager`）；镜像源支持「主源 + 备用源」依次重试，每个源最多 3 次，任一可用即可完成构建。
- 可配置：`docker-compose.yml` 通过构建参数传入镜像源，可在 `.env` 里设置 `NPM_REGISTRY` / `NPM_REGISTRY_FALLBACK`，或执行 `docker compose build --build-arg NPM_REGISTRY=<源>`。
- `.dockerignore` 排除 `core/data`、`/data`、`*.zip`、`*.bak` 等运行期数据与打包产物，构建上下文从几百 MB 降回源码体积。
- `.env` 模板补充镜像源说明；老版本生成的 `.env` 会在下次启动时自动补上这几行注释提示。

### 2026-10-29 · v2.9.3 · 完整部署包不再重复构建前端

- 现象：下载 `*-full.zip` 解压后执行 `./start.sh` 选 1 或 2，仍然看到前端在重新构建。
- 根因：`core/Dockerfile` 无条件执行 `pnpm install --frozen-lockfile` + `pnpm build:web`；同时 `.dockerignore` 里排除了 `web/dist`，所以即使完整包自带构建产物，Docker 构建时也拿不到、只能重来一遍。
- 修复：`core/Dockerfile` 改为「存在 `web/dist/index.html` 就跳过前端依赖安装与构建」，只有源码包才现场构建；`.dockerignore` 不再排除 `web/dist`（只排除仓库根目录的 `/dist`）。
- `start.sh` 的 Docker 模式启动前会明确打印「复用包内已构建的前端产物」或「未找到前端产物，会现场构建前端」。
- 发行说明模板 `.github/release-notes.md`、包内 `使用说明.txt`、README 都补充了完整包与源码包的区别说明。

### 2026-08-19 · 内置微信扫码、版本同步与运行自愈

- 移植进程内应用宝登录协议：通过微信 OAuth 扫码取得会话，再由内置 MMTLS 协议换取农场微信小游戏 Code，不再要求额外部署 YYB-GO 或第三方登录服务。
- “添加账号”开放微信扫码标签；进入标签后自动获取二维码，二维码空态和按钮均可手动获取或刷新。
- 修复扫码请求未携带面板登录 Token、后端无法识别当前用户的问题；扫码会话按当前用户隔离，避免多用户之间串用凭证。
- 微信扫码账号持久化 `loginBuffer`、`refreshtoken` 和 `accesstoken`，账号列表接口不向浏览器返回这些敏感字段。
- 扫码添加成功后默认启动账号，并自动开启“自动刷新获取 Code”，默认间隔为 60 分钟；已有内置凭证的旧微信账号会执行一次默认配置迁移。
- 每 30 分钟主动滚动保活应用宝凭证；手动启动、程序启动和定时刷新会优先通过内置协议获取新 Code，成功后更新账号并重启 Worker。
- 账号被踢或 WebSocket 多次重连失败后，可按自动刷新间隔延迟重登，并保留防止旧 Code 循环重连的停止行为。
- 保留外部微信登录 API 作为旧账号兼容回退；具备 `loginBuffer` 的新扫码账号不会回落到外部 API。默认不要求代理池，若网络环境确需代理，应使用账号固定出口而非随机轮换。
- 接入 WebSocket 服务端版本自动校准：登录回包和心跳回包会检查 `version_force`、`version_recommend`，优先采用强制版本并将完整客户端版本持久化到系统配置。
- Worker 检测到版本变化后上报主进程，主进程同步更新运行时和配置文件，后续 WebSocket URL、登录请求及心跳请求使用新版本。
- 已完成微信二维码在线生成验证、前端类型检查与生产构建；完整凭证生命周期仍需持续运行观察，凭证被撤销或过期时需重新扫码。
- 微信账号 WebSocket 登录返回 400 时接入内置应用宝刷新链路，刷新凭据和农场 Code 后自动重启账号；同账号同时触发的刷新会合并，避免滚动 Token 并发覆盖。
- 增加 Worker 看门狗：每 30 秒探测、90 秒无响应自动重启；一小时内最多自动重启 3 次，超限后停止账号。
- 增加自动恢复熔断：单账号每日最多 8 次恢复，连续刷新失败 3 次后停止自动尝试，成功恢复会清零连续失败计数。
- 账号接口不再接受客户端直接提交 `loginBuffer`、Refresh Token 或 Access Token；更换 `wxid` 时自动清空旧凭据，只有与当前面板用户绑定的有效扫码会话可以写入新凭据。
- 本次未包含业务请求合并、心跳请求容量预留和资源包完整性校验；这些运行质量优化仍属于后续范围。
