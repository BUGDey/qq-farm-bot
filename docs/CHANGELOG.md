## 详细记录
### v2.16.10 · 示例数据脱敏（2026-11-10）

**问题**：`account-identity.js` 的注释与两个测试用例里，把某个真实 QQ 号与真实昵称当成了示例值，随代码一起进了公开仓库。用户数据目录 `core/data/` 本身一直在 `.gitignore` 里（`git ls-files core/data` 为空，`accounts.json` 从未被提交），但**示例值**这层漏了。

**处理**：注释与测试里的 QQ 号改成 `10001000`、昵称改成「测试账号」，行为与断言逻辑不变。

### v2.16.9 · QQ 已运行时长跳变（2026-11-10）

**现象**：QQ 账号刚登录时「已运行」是对的，过一会儿跳一下，之后就比真实时间长得多；微信账号正常。

**原因**：锚点（`loginSince`）缺失时用 `Date.now() - workerUptime` 反推起点。但锚点被清（手动启动、被踢、触发下线提醒）的那一刻，worker 可能还是上一个会话的进程，`uptime` 是旧时长，反推回去就把旧时长接上了 —— 显示上就是「先对、再跳、之后不准」。另外展示值取了 `max(workerUptime, now - since)`，同样会把旧时长顶上去。

**修复**：
- 锚点一律取「此刻」，不再用 worker uptime 反推。
- 展示值只用锚点计算，不再和 worker uptime 取 max（`sessionUptime` 仍保留给经验效率用）。
- 手动启动 QQ 账号（`data-provider.startAccount`）先清锚点，等价于「这次扫码/填码重新计时」。
- 触发下线提醒（离线满 1 分钟）时清锚点。
- 新增 `core/test/runtime-uptime.test.js` 4 项覆盖上述边界。

### v2.16.8 · 顶号死循环与排行榜归属（2026-11-09）

**现象**：两个微信账号反复「被踢下线（已在其他终端登录）→ 自动刷新 Code 成功 → 重启 → 又被踢」；排行榜日榜出现名字叫「神秘农场」的行，实际账号早已删除。

**原因**：
1. 被外部顶号后仍无条件走 `scheduleAutoRelogin`，重登成功又把对面顶回去，双方互相踢。
2. 定时刷新 Code 不看最近是否被顶过，到点就把号重新拉回战场。
3. 排行榜遍历 `data/stats/*.json`，已删除账号的统计文件还在，`name` 取不到就显示兜底名——就是那条幽灵行。

**修复**：
- 新增 `core/src/services/kick-guard.js`：30 分钟窗口内被外部顶号超过 3 次即判定「不要再自动重登」，`isRecentlyKicked()` 供定时刷新避让；网络类原因不计入。
- `worker-manager` 的 `account_kicked` 分支接入该判定，命中时写日志「已停止自动重登（继续重登只会互相顶）」。
- `auto-code-refresh` 的定时器在账号刚被顶过时跳过本轮并提示。
- 新增 `core/src/services/account-identity.js`：以 `qq:<uin>` / `wx:<openId|wxid>` 作为稳定身份，`addOrUpdateAccount` 时把旧 id 的统计迁移到新 id，删号重登不会丢数据。
- `GET /api/ranking` 跳过 `_identities.json` 等索引文件，且只统计现存账号；删除账号的数据留在磁盘封存。
- 前端兜底名由「神秘农场」改为「未命名农场」。


### v2.16.7 · 2026-11-08 · 掉线/被踢后「已运行」也清零

用户补充：自动掉线之后，再扫码登录应该重新开始计时。

- `worker-manager.js` 新增 `resetLoginSince(accountId)`，在三条「账号非正常停止」的路径上调用：
  1. `ws_reconnect_failed`（多次重连失败，已自动停号）；
  2. `account_kicked`（被踢下线）；
  3. `ws_400` 且是 QQ 号（Code 失效、必须重新扫码）。
- 微信号 `ws_400` 走自动刷新 Code 后能自愈，**不清零**，避免把累计时长误清。
- 配合 v2.16.6 的「换凭证即清零」，现在无论是手动停止、重新扫码还是掉线停号，「已运行」都会从下一次登录重新算起。

### v2.16.6 · 2026-11-08 · 重新扫码后「已运行」重新计时

用户反馈：刚扫码登录没多久，首页「已运行」显示 `6天 21:23:19`，另一个号显示 `17:02:23`。

- **机制回顾**：`loginSince` 是持久化在账号记录里的计时锚点，`applySessionUptime()` 用它把 worker 自己会归零的 uptime 还原成累计时长。当初这样设计是为了让「自动刷新 Code 重启 worker」不清零。
- **问题**：这个锚点只有**手动停止账号**时才清（`clearAccountLogin`）。重新扫码走的是「保存账号」，没清锚点，于是一个 6 天前首次登录过的账号，重扫后继续从 6 天前算起。
- **修复**：`admin-account-routes.js` 在保存账号时比较 `loginBuffer`，发现凭证变化就 `clearAccountLogin`，让「已运行」从这次扫码重新计时；自动刷新 Code 不经过该接口，因此不会把累计时长清零。

### v2.16.5 · 2026-11-08 · Windows 恢复「拿完 Code 退掉 QQ」，改为全部号就绪后统一释放

v2.16.3 为了止住「一个号掉线、其他号跟着掉」，把「拿完 Code 就登出 NapCat」整个去掉了。
但那条逻辑原本是给 **Windows** 用的：NapCat 握着 QQ 登录会**抢占本机 QQ**，用户电脑上的 QQ 被挤下线。Linux / macOS 没有这个现象。

- **Windows**：所有在跑的 QQ 号都连上游戏后（每个号上报 `qq_code_consumed`），主进程等 3 秒统一 `releaseIdleSession()` 一次。
  这样既把 QQ 还给本机，又不会在别的号还需要重连时提前失效凭证。
- **Linux / macOS**：不释放，重连仍可复用原 Code。
- **扫码进行中**（`napcat-login.hasActiveTasks()`）跳过本轮释放，不会踢掉正在扫的号。
- **代价**：Windows 上释放之后，如果某个号后续被重启，它需要重新扫码（QQ 号本来也没有可再生凭证）。

### v2.16.4 · 2026-11-08 · 邀请奖励改为「绑定后才发」，并挡住小号复用同一游戏号

原实现里被邀请人**注册就立刻到账**，只要有一台挂机账号，就能不停注册小号刷天数。
现在改成**双方都待定**，等这个新号真正绑上一台挂机账号（账号创建时写入标识）再一次性发放。

- **绑定标识**：QQ 号取 `uin`，微信端取 `openId/wxid`，组合成 `platform:标识` 存进 `data/invites.json` 的 `identities`。
  这类标识不会因为重新登录、换设备而改变，可以当作「这台游戏账号归谁」的凭据。
- **一账号一奖励**：同一标识只能给一个注册用户结算。若第 3 个小号又绑了别人已用过的 `qq1`，`markInviteeBound` 直接判 `identity_reused`，记录标记为拦截，双方都拿不到天数；注册本身不受影响。
- **仍然不强制绑定**：不填邀请码、不绑账号都能正常用面板，只是拿不到邀请奖励。
- **后台可查**：邀请奖励页签的拦截原因里会多出 `identity_reused`，能直接看到是哪个账号想复用。

### v2.16.3 · 2026-11-08 · 修复「一个 QQ 号掉线，其他号跟着掉」

用户反馈：三个 QQ 号同时掉线，日志里全出现同一个账号的退出记录，怀疑是一个号重启牵连了其他号。

- **元凶：NapCat 自动登出。** v2.14.12 加过「拿到 Code 后把 QQ 从 NapCat 里登出」，但 NapCat 是所有 QQ 号**共用**的同一个实例。登出会让小程序会话失效，之后任何一次 WS 重连都拿到 `400`；而 worker 重启（看门狗、异常、手动）必然触发重连——于是一个号重启 → NapCat 已登出 → 重连 400 → 该号停 → 下个号重启同样 400，形成连环掉线。
  - 现在**拿到 Code 后不再登出**；只有当一个 QQ 号都不在跑时（`stopWorker` 后 2 秒检查），才放掉 NapCat 里的 QQ 会话。
- **看门狗误杀。** `WATCHDOG_TIMEOUT_MS` 90 秒、且一次没回心跳就重启；worker 正在处理长任务时很容易踩线，而误杀一次就要用旧 Code 重连。现在放宽到 **180 秒**，并要求**连续两次**都没心跳才重启（`wrk.watchdogMisses`）。
- **QQ 号不再无限重试。** QQ 号没有可再生凭证，按阶梯重试只会反复撞 400、刷屏并拖累其他号。现在 `ws_400` 分支判断平台：QQ 号直接停止并提示「Code 已失效，请重新扫码」，微信号才走自动刷新。

### v2.16.2 · 2026-11-08 · 网关健康上报与停止语义

- **健康快照**：`core/src/runtime/gateway-client.js` 的 `getGatewayHealth()` 原来返回一个从不更新的空对象，在途请求恒为 0。现在按 `pending` 统计请求数与最老耗时，`isGatewayIdleForLowPriority()` 也改为看真实在途数——否则后台任务永远觉得自己最闲，会一起涌上来压垮连接。
- **断线可恢复**：网关进程挂掉时 socket 会 close，旧实现里 `reconnect()` 是空函数，worker 之后再也收不到 `login`。现在 `reconnect()` 会重建 socket 并带**原 Code** 重新握手；网关仍持有连接时走 `reused`，不会多消耗一个凭证。
- **停止语义**：`stopNetwork()` 会把挂起请求立即 reject（原来要等 30 秒超时）；网关进程收到 `stop` 后自行退出，避免残留僵尸网关占着管道。
- **错误回传**：网关的 `ws_error`（如 `400 Unexpected server response`）会记录并回传，`getWsErrorState()` 能拿到，上层据此提示「Code 失效，请重新扫码」而不是笼统的离线。
- **日志合并**：网关进程的 `log` 帧并入 worker 日志，排查时一条日志看得全。

### v2.16.1 · 2026-11-08 · 邀请奖励与心跳误判修复

- **邀请奖励**：新增 `core/src/services/invite-rewards.js`（与游戏内的分享码 `services/invite.js` 完全分开，互不影响）。

  - 后台「邀请奖励」页签：启用开关、双方天数、各项限额、`requireBoundAccount` 开关、拦截原因归类与明细。

### 2026-11-01 · v2.11.11 · 已运行时长按首次登录累计

- **现象**：日志里「自动刷新 Code 成功，已重启账号」之后，首页「已运行」又从 `00:00:00` 开始；访问凭证倒计时是单独的，本来就该按新凭证重新计时。
- **原因**：worker 进程内的运行计时（`accountRunStartedAt`）随进程重启归零，重启后上报的 `uptime` 自然从 0 开始，面板直接拿它显示。
- **改法**：账号记录新增 `loginSince`（首次登录成功时间戳），只在第一次登录时写入；主进程收到状态时用 `now - loginSince` 还原累计时长。刷新 Code 走的是 `restartWorker`，不经过 `stopAccount`，因此不会清空；只有用户手动「停止」账号才调用 `clearAccountLogin` 重新计时。
- **副带**：状态里新增 `sessionUptime`（本次进程运行时长），「EXP 效率」「升级预估」改用它会话时长，避免用累计时长算出偏低的速率。
- **验证**：新增 `account-login-since.test.js` 覆盖「只写一次 / 更新账号不丢 / 手动停止后清空」，全量单测 565 项通过。

### 2026-08-19 · 内置微信扫码、版本同步与运行自愈

- 移植进程内应用宝登录协议：通过微信 OAuth 扫码取得会话，再由内置 MMTLS 协议换取农场微信小游戏 Code，不再要求额外部署 YYB-GO 或第三方登录服务。

- 微信扫码账号持久化 `loginBuffer`、`refreshtoken` 和 `accesstoken`，账号列表接口不向浏览器返回这些敏感字段。
- 扫码添加成功后默认启动账号，并自动开启“自动刷新获取 Code”，默认间隔为 60 分钟；已有内置凭证的旧微信账号会执行一次默认配置迁移。
- 每 30 分钟主动滚动保活应用宝凭证；手动启动、程序启动和定时刷新会优先通过内置协议获取新 Code，成功后更新账号并重启 Worker。
- 账号被踢或 WebSocket 多次重连失败后，可按自动刷新间隔延迟重登，并保留防止旧 Code 循环重连的停止行为。
- 保留外部微信登录 API 作为旧账号兼容回退；具备 `loginBuffer` 的新扫码账号不会回落到外部 API。默认不要求代理池，若网络环境确需代理，应使用账号固定出口而非随机轮换。
- 接入 WebSocket 服务端版本自动校准：登录回包和心跳回包会检查 `version_force`、`version_recommend`，优先采用强制版本并将完整客户端版本持久化到系统配置。
- Worker 检测到版本变化后上报主进程，主进程同步更新运行时和配置文件，后续 WebSocket URL、登录请求及心跳请求使用新版本。
- 已完成微信二维码在线生成验证、前端类型检查与生产构建；完整凭证生命周期仍需持续运行观察，凭证被撤销或过期时需重新扫码。
- 微信账号 WebSocket 登录返回 400 时接入内置应用宝刷新链路，刷新凭据和农场 Code 后自动重启账号；同账号同时触发的刷新会合并，避免滚动 Token 并发覆盖。
- 增加 Worker 看门狗：每 30 秒探测、90 秒无响应自动重启；一小时内最多自动重启 3 次，超限后停止账号。
- 增加自动恢复熔断：单账号每日最多 8 次恢复，连续刷新失败 3 次后停止自动尝试，成功恢复会清零连续失败计数。
- 账号接口不再接受客户端直接提交 `loginBuffer`、Refresh Token 或 Access Token；更换 `wxid` 时自动清空旧凭据，只有与当前面板用户绑定的有效扫码会话可以写入新凭据。
- 本次未包含业务请求合并、心跳请求容量预留和资源包完整性校验；这些运行质量优化仍属于后续范围。
