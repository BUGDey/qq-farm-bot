# 项目硬约定（AGENTS.md）

来源：仓库根目录 `AGENTS.md`。这些是长期积累的**项目级规矩**，改动活动、植物或前端时容易踩。

## 一、官方源码位置（macOS）

```text
展开源码：~/Library/Containers/com.tencent.qqexminiprogram/Data/Library/Application Support/QQEX/miniapp/temps/miniapp_src/
运行资源：~/Library/Containers/com.tencent.qqexminiprogram/Data/Library/Application Support/QQEX/miniapp/fs/*/1112386029/usr/gamecaches/
资源映射：.../usr/gamecaches/cacheList.json
微信缓存：~/Library/Containers/com.tencent.xinWeChat/Data/.wxapplet/
```

AppID `1112386029`，版本目录匹配 `1112386029_3_*`。
**每次 QQ 农场更新后目录尾部哈希都会变化，不要把某个哈希目录永久视为最新版**，
应按其中 `tsdk/tsdk.wasm` 的修改时间排序选最新且完整的目录。

候选目录至少应包含：`game.js`、`game.json`、`tsdk/tsdk.wasm`、`assets/`。

分析官方文件时只读源目录，先复制到临时目录再处理，不要直接修改 QQ 容器缓存。

## 二、限时活动适配核心流程

先把官方数据来源和协议边界摸清楚，再落代码。从最新版 `miniapp_src`、运行资源缓存、
HAR/WS 抓包和已有 proto/service 中**交叉确认**：

- 活动 ID、子活动 ID、命令字、活动开始/结束时间、服务端时区和状态字段。
- 活动货币、消耗品、奖励、装扮、礼包、特殊作物、特殊天气/效果等物品 ID 与图片资源。
- 每个动作的前置条件、每日/活动限额、返回字段和失败码；**不要只凭 UI 文案猜协议**。
- 是否存在作物大小、变异类型、天气状态、好友状态等会影响核心自动化的隐含字段。

### 活动 Operate 协议静态恢复

遇到 `ActivityService.Operate` 字段不明、动态抓包没命中、账号已无可操作次数，或仓库 proto
与客户端行为不一致时，使用项目技能 `$qq-farm-activity-protocol-recovery`
（`.agents/skills/qq-farm-activity-protocol-recovery/`）恢复官方生成协议。

**不得猜测字段号**，不得把枚举或 hook 候选、官方编码器重构、加密抓包误报成 protobuf 明文抓包。
官方 QQ 容器目录只读；真实账号请求仍须用户在当前任务中明确授权。

### 后端适配顺序

先补齐可复用的数据模型和只读查询，再接入自动执行流程：

- 在活动 service 中标准化活动状态、任务进度、奖励、商店、研究/阶段等结构，
  **前端只消费已归一化的数据**。
- 新增协议或 proto 字段时同步补解析、脱敏检查和最小测试；不要把未知字段硬编码成
  一次性字符串拼接逻辑。
- 活动物品名称、图标、种子/作物、变异类型等必须进入统一配置或补充配置，
  避免页面显示"未知物品"或自动流程识别失败。
- 自动流程只在账号已启动、活动有效、对应账号开关开启、限额未耗尽且资源足够时执行；
  **失败要可观测，不能阻塞其他常规任务**。

### 前端活动页与设置页职责必须拆开

- 活动页贴合游戏 UI 风格，可同时承载状态展示与手工操作（购买、领取、使用、解锁、赠送、采集）。
  但**不写"去哪里操作/怎么使用"的流程说明**，操作应自解释。
- **手工操作入口必须复用与自动化相同的后端动作和前置校验**，不得为页面单独实现一套绕过限额、
  资源检查或活动有效期判断的捷径。涉及钻石等强付费资源的操作，后端已有的拒绝逻辑不得放宽。
- 能抽离成周期性后台动作的功能，还必须在 `设置 → 账号设置 → 日常与活动` 提供自动化开关，
  按活动新建二级卡片；每个开关名称应对应一个后台自动动作（自动购买、自动采集、自动使用、
  自动研究）。**纯前端状态标记（如已读动画）和一次性配置项（如跳过战斗动画）不属于自动化动作，
  不要为其建开关。**
- 旧版自动控制页若仍存在同类入口，要与账号设置保持同一批配置字段和同一套显隐规则，
  避免一个页面隐藏而另一个页面仍能打开过期任务。

## 三、活动页面 UI 与状态同步

活动页面以**高频查看和快速判断**为目标，不要把协议字段逐项堆成通用后台卡片。
开始设计前先从官方 Prefab、运行资源缓存和活动数据中确认页面分区、阶段关系、状态名称及可用图片。
**官方素材存在时优先使用真实活动标题、场景或物品资源**，不用与活动无关的通用渐变和装饰替代。
无法可靠提取官方资源时可沿用项目现有组件和图标，但**不得臆造奖励、阶段关系或操作规则**。

- 首屏优先展示活动名称、结束时间、核心环境状态，以及最重要的货币或物品库存。
  每日剩余次数、当前可推进阶段等决策信息应比重复库存更醒目；
  **同一数值不要在相邻区域重复做主信息展示**。
- 活动结束时间和临时效果结束时间**必须包含日期和时间**，避免跨天时只显示时分造成误解。
  服务端时间需按已确认的时区解析，**不能由组件自行猜测**。
- 每日任务应展示明确的 `progress/target`、进度条和完成状态；
  **`target` 缺失、为零或协议仍未确认时不得伪造分母**。奖励名称、数量和图标应来自
  归一化模型或统一物品配置。
- 存在前置节点的研究、阶段、桥梁或通行证应使用有顺序含义的轨道、步骤或连接关系，
  至少区分**已完成 / 当前可推进 / 未解锁**三种状态，并明确当前节点的消耗与奖励；
  不能仅用无关系的平铺卡片。
- 移动端首屏保持紧凑：固定格式的库存和状态项使用稳定网格或横向布局，避免每项独占一行；
  文本、状态徽标和长物品名不能溢出或遮挡。桌面端增加列数时仍需保持阅读顺序和阶段连接正确。
- 加载中、无账号、无数据、协议读取失败和活动失效**必须有独立状态**，不能用全零数据冒充成功响应。
  刷新按钮需要加载与禁用反馈，**不允许并发重复请求**。
- 后台自动购买、使用、采集、领取或研究完成后，活动页不能长期保留旧进度。
  活动有效且页面可见时应使用低频轮询或已有事件机制同步；**页面重新获得可见性时立即刷新，
  隐藏时停止请求**，并与手工刷新去重。活动结束后必须停止该同步逻辑。
- 官方 Prefab 中的"购买""去使用""解锁"等按钮可作为页面交互与视觉的参照，
  但据此实现的手工操作入口必须走本项目已有的后端动作与前置校验。

## 四、Codex 与人工 UI 验收边界

修改前端页面后**只需完成类型检查、生产构建和明显报错检查**，不需要代替用户启动浏览器进行
桌面端、移动端或真实账号的视觉与交互验收。页面布局、素材裁切、实际数据状态和交互体验由用户
自行人工验证；交付说明中应明确**已完成的自动检查及仍待人工确认的部分**。

除非用户在当前任务中明确要求，**不要自行启动本地浏览器、登录账号或执行真实账号活动操作**。

但因为活动页含手工操作入口后类型检查与生产构建已不足以覆盖状态流转，**允许并鼓励为纯逻辑部分
补自动化测试**：store 的状态机与并发保护、前置校验与限额判断、时间边界与时区解析、协议编解码往返。
这类测试须使用**固定夹具或录制响应，不得连接真实服务端**。
视觉、布局、素材裁切和真机交互仍由用户人工验收。

每次活动适配完成前至少验证：

- 后端活动查询、关键动作解析、活动边界和**隐藏活动开关防回启**测试。
- 手工操作入口与自动化动作复用同一后端校验，且钻石等付费资源的拒绝逻辑未被放宽。
- 协议下发路径解析的素材，映射表与本地文件逐一对应且 sha256 匹配。
- 前端类型检查/生产构建，以及活动页没有残留待实现的手工操作入口。
- 过期、未开始、进行中、边界时刻、**历史开关已开启但活动已结束**等场景。

## 五、活动植物占地大小（易漏）

向 `core/src/gameConfig/EventPlants.json` 补充活动植物时，**不要只填 ID、名称和资源映射**，
必须同时核实作物占地大小。四格（2x2）作物需要显式填写 `size`：

```json
{ "id": 1029003, "seed_id": 29003, "fruit_id": 49003, "name": "星语铃花", "size": 2 }
```

**省略 `size: 2` 会使活动作物默认按单格处理**，导致它无法进入 2x2 优先种植与土地预留流程，
甚至被背包单格种植策略选中。新增或更新该字段时还要确认 `core/src/config/gameConfig.js` 将
`size` 透传到植物配置，并用测试断言 `getPlantBySeedId(seedId).size === 2`；必要时检查背包接口
返回的 `plantSize` 是否为 `2`。

## 六、种植等级判断中的 ≥ 200 级例外（易漏）

项目约定：**所需等级 ≥ `200` 的作物种子不参与本地种植等级限制**，此规则不限于 2x2 作物。

- 保留官方配置中的原始等级，**不要把所有 2x2 作物或种子的等级统一改为 `1`**。
- 低于 200 的等级（如 `31`、`199`）仍按账号等级正常判断；例外覆盖所有 ≥200 的等级。
- 新增或调整本地种植等级判断时复用 `isSeedLockedByLevel`，
  并补 ≥200 级豁免与普通等级边界测试。
- **商城购买解锁条件及服务端种植校验不因这条本地规则而放宽。**

## 七、活动入口按时间状态管理（易漏）

新增活动页面或活动控制开关卡片时，**必须配置并使用活动开始时间和结束时间**，
根据当前时间自动控制入口状态：

- 活动列表中的已登记活动卡片**不因未开始或已结束而隐藏**：卡片必须展示完整的开始日期时间和
  结束日期时间；未开始和已结束时置灰、显示对应状态并**禁止进入**，仅在有效期内允许进入详情。
- 页面路由等直接访问入口也应复用同一套有效期判断，避免通过直达路径进入未开始或过期活动页面。
- 时间边界、时区以及缺失或无效时间配置时的行为应明确。
- **每个活动还必须登记更新日期**；活动列表按更新日期倒序排列，最新更新在最上方，
  更新日期相同时再按活动开始时间倒序。**不得依赖模板中的硬编码书写顺序。**
- 设置页的活动自动化开关和旧版自动控制入口仍只在活动有效期内显示。
  **活动列表卡片的历史留存与自动化入口显隐是两套职责**，不得因隐藏自动化开关而移除活动列表记录。
- **活动结束后不能只把卡片置灰**：如果用户此前开启了该活动的任务开关，必须自动将对应的
  持久化开关状态关闭，并停止、取消或阻止该活动相关的定时任务、轮询和后台执行逻辑；
  应用启动、配置加载和任务调度前也必须校验活动有效期，确保过期任务不会因历史配置再次启动。
- 应为开始前、进行中、结束后、边界时刻，以及"活动结束时开关仍处于开启状态"的场景补充测试。
